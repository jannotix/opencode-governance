# OpenCode Governance v3.2 — Architect Phase Failover

**Status:** Approved for implementation  
**Date:** 2026-07-28  
**Base:** OpenCode Governance 3.1.0  
**Target:** 3.2.0

## Purpose

Extend the v3.1 bounded failover mechanism to the authoritative Architect role used by Architect, governed Build and governed Plan entry points.

## Safety boundary

Architect failover restarts one complete governance phase. It never continues a partial model response and never resumes from unverified partial `.ai/**` writes.

Hidden aliases use:

```text
architect-fallback-1
architect-fallback-2
```

They are internal routing transports for the existing Architect authority. They use `mode: subagent`, `hidden: true` and `task: deny`. They complete only the current Architect-owned phase and return control to the public Architect/Build orchestrator.

## Phase transaction

Before every failover-eligible Architect phase, create `GOVERNANCE_PHASE_SAFEPOINT` containing:

```text
PHASE_ATTEMPT_ID
PHASE_NAME
TASK_ID
INPUT_PACKET_SHA256
FROZEN_TARGET_SHA
RUN_STATE_SHA256
AFFECTED_GOVERNANCE_PATHS
PRE_PHASE_FILE_HASHES
CHECKPOINT_PATH
CHECKPOINT_COMPLETE: YES
```

Checkpoint content is stored under the existing task evidence tree:

```text
.ai/tasks/<TASK-ID>/evidence/checkpoints/<PHASE_ATTEMPT_ID>/
```

Only files listed in `AFFECTED_GOVERNANCE_PATHS` are copied. Secrets are excluded.

During an attempt, phase output is not authoritative until the phase reports:

```text
PHASE_REPORT_COMPLETE: YES
PHASE_ATTEMPT_ID: <matching>
INPUT_PACKET_SHA256: <matching>
FROZEN_TARGET_SHA: <matching>
```

## Failure recovery

On an eligible primary or fallback failure:

1. reject the partial response and partial phase report;
2. stop all consumers of the current phase output;
3. restore every affected governance file from `GOVERNANCE_PHASE_SAFEPOINT`;
4. remove only attempt-created files listed in the attempt journal;
5. verify post-restore hashes against `PRE_PHASE_FILE_HASHES`;
6. keep input packet and frozen target unchanged;
7. select the next eligible Architect route;
8. restart the complete phase.

If rollback is incomplete, hashes differ, the checkpoint is missing, or unjournaled `.ai/**` changes exist, return:

```text
ARCHITECT_FAILOVER_BLOCKED
HUMAN_RECOVERY_REQUIRED
```

No fallback starts from a dirty governance phase.

## Eligible phases

Failover may apply to Architect-owned phases including:

```text
PRODUCT_CLASSIFICATION
ADAPTIVE_DISCOVERY
GOVERNED_DOMAIN_RESEARCH
CONSTRUCTIVE_CHALLENGE
PRODUCT_DEFINITION
PRODUCT_SCOPE_APPROVAL
CONTEXT_ROUTING
DELIVERY_ARCHITECTURE
VERTICAL_MILESTONE_PLANNING
EVIDENCE_ROUTING
PRODUCT_COMPLETENESS_RECONCILIATION
RELEASE_READINESS_COORDINATION
```

Implementation, reviewer and Final Reviewer attempts continue to use their own role policies.

## Entry-point behavior

- `architect`: restarts the current Architect phase.
- `build`: uses the same Architect phase policy and returns to the full workflow after phase completion.
- `plan`: uses the same Architect phase policy but remains planning-only and never delegates implementation/review.

The hidden fallback alias itself never delegates. The public entry point performs later governed delegation only after accepting a complete matching phase result.

## Sticky fallback and primary re-entry

Once an Architect fallback phase starts, it is sticky until that phase finishes or fails. Primary recovery never interrupts it.

Primary is reconsidered only at the next phase boundary or later task after cooldown. It never restarts an already completed phase solely because its quota returned.

## Routing and independence

Architect fallback candidates use the same validated routing profile and concrete model/variant rules introduced in v3.1.

Architect family independence from downstream roles is desirable but not mandatory because Architect is not a reviewer of its own implementation. Existing reviewer and Final Reviewer independence rules remain controlling.

## Compatibility

- Legacy single-model installation remains supported.
- v3.1 reviewer-only profiles remain valid.
- Architect fallback is enabled only when `architect` appears in `settings.enabled_roles` and has configured fallbacks.
- Seven public governance agents and twelve commands remain unchanged.
- No Executor failover is activated in v3.2.

## Acceptance criteria

1. Existing v3.1 profiles install unchanged.
2. Architect-enabled profiles render hidden `architect-fallback-*` aliases.
3. Architect and Build may invoke configured Architect fallback aliases; Plan cannot delegate and records a blocked handoff for external orchestration.
4. Hidden Architect aliases deny delegation.
5. Missing or incomplete phase safepoint blocks failover.
6. Hash mismatch after restoration blocks failover.
7. Partial phase output is never authoritative.
8. Fallback restarts the entire phase with matching packet/target/checkpoint identifiers.
9. Active fallback is never preempted by primary recovery.
10. Primary is reconsidered only at a later phase boundary/task.
11. Windows and Linux CI cover reviewer-only compatibility, Architect routing, invalid safepoint state and conservative uninstall.
